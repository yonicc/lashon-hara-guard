# 35 — הזנת זיכרון מקומי ובדיקת DB בדפדפן

תאריך: 2026-10-28. המשך ל־docs/33. אבטיפוס נפרד ב־`research/local-memory/`.
לא שונו התוסף החי, שירותים או חוזה `/check`. נתונים סינתטיים בלבד.

## האם המחקר הקודם הגדיר מי מזין ומתי?

לא במלואו. docs/33 הגדיר אחסון, embeddings ושליפה, ותיאר את החנות הקיימת.
לא הוגדר בו חוזה הזנה עם זהות חשבון, זהות הודעה, עדכונים ומחיקה.

בקוד הקיים `extension/context-runtime.js`:
- `prepare` מזהה שיחה ומייצר packet; רק כאשר `remember=true` מתבצעת `builder.ingestMessage`.
- מזהי השיחות הם זמניים לסשן. אין שם זהות חשבון יציבה שמספיקה לארכיון מתמשך.
- `context-store.js` שומר IndexedDB המשויך לאתר, כפי שמתועד ב־PRIVACY.md.
לפיכך אין להניח שהחנות הנוכחית היא DB משותף לכל הפלטפורמות של התוסף.

## בעלות ותזמון — חוזה ההזנה לשילוב הבא

הטבלה היא תכנון השילוב; באבטיפוס האירועים מוזנים באופן סינתטי בלבד.
הכתיבה, ההטמעה והשליפה עצמן כבר ממומשות ונבדקו.

| מה | מי אחראי | מתי | מה נשמר / מגבלה |
|---|---|---|---|
| הודעות קיימות בחלון השיחה | מתאם DOM של הפלטפורמה | פתיחת שיחה, לאחר זיהוי חשבון ושיחה ובדיקת מתג הזיכרון | snapshot מוגבל של הודעות שנצפו; אין טעינת כל הארכיון או גלילה אוטומטית |
| הודעה נכנסת חדשה | אותו מתאם | זיהוי הודעה שלמה עם ID יציב, לפני המתנה בתור בדיקה | אירוע `message_observed`; אין תלות בהצלחת בדיקה מרוחקת |
| טקסט שמוזן בשדה מאובחן | מתאם השדות של התוסף | בכל הזנה/שינוי טקסט באתר נבחר; איחוד אירועי הקלדה צפופים מותר, לפני מעבר שיחה יש להשלים snapshot | `input_observed`; רשומת draft מתעדכנת לפי ID של שדה/compose, גם לפני שליחה |
| קונטקסט נוסף ממייל/שיחה | אוסף הקונטקסט של התוסף | בכל איסוף לצורך אבחון, יחד עם snapshot של ה־scope | `context_observed`; רשומת context עם מקור מובחן, לא הודעה שנשלחה |
| הודעה יוצאת שנשלחה | מתאם הפלטפורמה | הופעת ההודעה ברשימה / אישור DOM אמין | רשומת message נפרדת; מעבר מ־draft ל־message דורש קישור מקור אמין ואינו מונח מעצמו |
| עריכת הודעה | אותו מתאם | שינוי תוכן עבור אותו message ID | `message_edited`; החלפה אטומית של טקסט ווקטור, ללא הארכת תוקף |
| מחיקה מפורשת במקור | אותו מתאם | סימון מחיקה אמין עם ID מוכר | מחיקת הרשומה והווקטור; היעלמות עקב virtualization אינה מחיקה |
| מעבר חשבון/שיחה | המתאם | ברגע הזיהוי, לפני תור async | capture של scope; מידע מתור ישן נשאר ב־scope המקורי |
| embeddings | owner יחיד מקומי של ה־DB | אחרי קבלת אירוע תקין, בתור כתיבה סדרתי | e5 `passage:`; כשל אינו שומר טקסט עם וקטור ישן |
| עובדות וקשרים מאומתים | המשתמש, דרך UI ייעודי עתידי | רק לאחר אישור מפורש ומוגבל ל־scope ותוקף | אינם נלמדים כאמת מהודעות או מדמיון וקטורי; לא מומשו באבטיפוס |
| חיפוש למודל | כלי קריאה קשור ל־scope מהיישום | כשהנתב מבקש הרחבת קונטקסט | `query:`, עד 3 תוצאות × 300 תווים; candidate בלבד |
| ניקוי | owner ה־DB | באתחול ובטיימר תקופתי בשילוב העתידי | 14 יום; בנוסף כל קריאה מסננת תפוגה; ניקוי מוחק גם וקטורים |
| מחיקת שיחה / הכל | בקרות המשתמש | בקשה מפורשת | מחיקת רשומות ווקטורים באותו מסד |

החלטת בעלים במהלך העבודה: כל הזנת טקסט בשדות המאובחנים באתרים הנבחרים,
וגם קונטקסט נוסף שנאסף ממייל וכדומה, יוזנו למסד. אין להתנות שמירה בשליחה.
אין הכוונה לזחלן של כל שדות האתר: מקור האירועים הוא רק השדות והקונטקסט שהתוסף מאבחן.
זהו חוזה השילוב המאושר; המימוש הנוכחי מקבל אירועים סינתטיים מאותם סוגים,
וטרם חובר ל־DOM החי. מניעת כפילות בין draft לבין הודעה שנשלחה נדרשת בשילוב המתאמים.

המודל אינו מזין את ה־DB ואינו מוסמך לאמת עובדות. הוא קורא מועמדים לקונטקסט.
זיכרון כבוי כברירת מחדל בשילוב עתידי עד מתן בחירה מפורשת; באבטיפוס כל אירוע דורש
`enabled:true`. זו בדיקת ספרייה, לא מסך הסכמה או מתג מוצר שכבר הותקן.

אין איסוף בלי `platform + accountId + conversationId + sourceId` יציבים.
שמות תצוגה וכותרות אינם זהות מספקת. אם אין דרך אמינה לזהות חשבון/הודעה בפלטפורמה,
אותו מתאם חסום לשמירה מתמשכת עד שייבדק ב־DOM; קונטקסט זמני ובדיקה רגילה יכולים להמשיך.
אין למזג אנשים בין פלטפורמות אוטומטית. מקור הודעה אינו ראיה לאמיתות הטענה שבה.

## מה מומש בפועל

`memory.mjs`: IndexedDB אמיתי עם טקסט + Float32Array באותה רשומה;
זהות מורכבת; dedup; עריכה; דחיית אירוע ישן; תור כתיבה יחיד; מחיקה ותפוגה;
מגבלת 20,000 רשומות כללית ו־1,000 תווים; אין fallback שמדמה persistence.

`embedding.mjs`: multilingual-e5-small quantized, 384 ממדים, mean pooling,
נרמול, CPU/WASM בדפדפן. כל משקלי המודל וה־WASM נטענים מהדיסק דרך loopback;
הורדה ראשונית נדרשת בנפרד. אין בקשת inference מרוחקת.

`memory.tools(scope)` נותן שני כלים בלבד:
- `get_recent({k:1..5})`
- `search_history({query,top_k:1..3})`

ה־scope נקשר ביישום, לא נבחר על ידי המודל. אין SQL או כלי כתיבה למודל.
תוצאה שומרת `provenance:dom_observed`, `status:candidate`, זמן תצפית ו־ref,
וכן `kind: draft|context|message`, כדי שלא לייחס לטיוטה מעמד של הודעה שנשלחה.
ציון cosine הוא דירוג של דמיון בלבד; אין סף איכות מכויל ואין הסקת אמת.
הלולאה והמודל המנתב של docs/34 טרם אומנו או שולבו.

## בדיקות ומדידות אמיתיות

הרצה ב־Chrome 155 headless ב־Windows על BI-1, פרופיל זמני נפרד.
הבדיקה סגרה ופתחה מחדש את תהליך הדפדפן; המידע נשמר ב־IndexedDB.
26 בדיקות עברו; פירוט מלא וקלטי הבדיקה בקוד ו־`browser-results.json`.

| מדד | תוצאה |
|---|---:|
| טעינת מודל מקבצים מקומיים קיימים | 1,164ms |
| הזנת 3 הודעות כולל embeddings וכתיבה | 105.2ms |
| הכנסת fixture של 2,000 רשומות ב־transaction | 110.4ms |
| שאילתה מלאה: embedding + קריאת IDB + דירוג, p50 | 44.8ms |
| אותה שאילתה מלאה, p95, 30 חזרות חמות | 51.6ms |
| בקשות דפדפן מחוץ ל־loopback | 0 |

ה־fixture משכפל וקטורים אמיתיים ממספר קטעים סינתטיים. זה מבחן עומס אחסון/שליפה,
לא מדידת איכות על 2,000 הודעות שונות או מדידת קצב הזנה של 2,000 embeddings.
נבדקה התאמה סמנטית בעברית: ״מתי יתקנו את המכונית?״ מחזירה הודעה על הרכב במוסך.
זה smoke test אחד, לא benchmark איכות עצמאי.

נבדקו הפרדה בין חשבונות ובין שיחות; dedup; דחיית הזנה כבויה; מגבלת top_k;
זהות חסרה; עריכה; מחיקה בזמן הזנה; מחיקת שיחה בלי מחיקת חשבון אחר;
תפוגה בקריאה ומחיקה פיזית של טקסט+וקטור; clear; persistence אחרי restart.
יעד 50ms של docs/33 אינו מוכח מקצה לקצה: p95 המלא שנמדד הוא 51.6ms,
כולל embedding. אין כאן הפרדת זמן השליפה בלבד, ואין מדידת 20k בדפדפן.

## הצעד הבא ומגבלות

יש כעת DB מקומי שהמודל יכול לתשאל דרך API מוגבל, וה־embedding באמת רץ בדפדפן.
ההמלצה: לשלב תחילה בגרסת ניסוי נפרדת של התוסף, עם owner יחיד ב־extension origin,
ולהעביר אליו אירועים מהמתאמים דרך הודעות מאומתות. לא לנסות לשתף ישירות חנויות
content-script המשויכות לאתרים. אין migration של מידע אמיתי באבטיפוס הזה.

השלב הבא דורש fixtures ל־IDs של חשבון/שיחה/הודעה בכל פלטפורמה, רגרסיית עריכות
ופיצול טקסט ארוך למקטעים: האבטיפוס דוחה במפורש רשומה מעל 1,000 תווים;
אין לטעון שכבר נקלט גוף מייל מלא בכל אורך, ואין לקצץ אותו בשקט.
ומחיקות ב־DOM, ו־MV3 offscreen lifecycle/restart. טרם נבדקו offscreen, WebGPU,
מספר כותבים, הצפנה, זיכרון RAM, מודל מנתב אמיתי או אינטגרציה חיה.
לפני שילוב מוצר יש לעדכן מדיניות פרטיות ומסכי שליטה; האבטיפוס אינו משנה
את מדיניות האיסוף של הגרסה המותקנת. לא בוצעה פריסה.
